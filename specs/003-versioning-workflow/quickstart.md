# Quickstart: Versioning and release workflow

A maintainer's experience from "fresh clone" through "first release shipped via the workflow." Treat this as a validation surface — if any of these flows fail to produce the documented outcome, an FR has been violated.

## One-time setup (after spec 003 lands)

Clone the repo and install dependencies:

```sh
git clone https://github.com/kendrick/unbranded-ds.git
cd unbranded-ds
pnpm install
```

Verify `@changesets/cli` is available:

```sh
pnpm changeset --version
```

Output should be a version number (e.g., `2.27.7`). If this command errors with "unknown command," the install step failed; investigate `pnpm install` output.

Verify the config file is in place:

```sh
cat .changeset/config.json
```

Output should show the configured fields (`access: "public"`, `baseBranch: "main"`, etc.). See [contracts/changeset-format.md](./contracts/changeset-format.md) for the full contract.

Read the contributor doc:

```sh
cat .changeset/README.md
```

This is the canonical contributor-facing reference. Skim it before your first PR.

## Per-PR workflow (the common case)

Open a branch and modify a published package:

```sh
git checkout -b feat/some-improvement
# ... edit packages/react/src/components/Button/Button.tsx ...
```

Run `pnpm changeset` from the repo root. The interactive prompt asks which packages changed and at what bump level:

```sh
pnpm changeset
```

Walk through the prompts:

1. **Which packages would you like to include?** Pick the affected packages with space; press enter to confirm. The `apps/storybook` workspace member does NOT appear (it's `ignore`d in the config).
2. **Which packages should have a major bump?** For a breaking change pre-1.0, also use `minor` here per pre-1.0 semver. For a non-breaking change, skip (just press enter).
3. **Which packages should have a minor bump?** For new features or pre-1.0 breaking changes. Skip if patch-only.
4. **Confirm patch for the rest?** Yes for any not-yet-bumped package.
5. **Summary**: a free-form text editor opens. Write the description per the FR-013 quality bar.

For a non-breaking change, the summary is one line:

```
Add `<Tooltip>` component wrapping `@base-ui-components/react/tooltip`. Slots: Trigger, Content, Provider.
```

For a breaking change, the summary is multi-paragraph with before/after examples (see [contracts/changeset-format.md](./contracts/changeset-format.md) for the breaking-change example).

After you save the summary, the command writes `.changeset/<auto-generated-slug>.md`. Commit it alongside your code change:

```sh
git add .changeset/ packages/react/src/components/Button/Button.tsx
git commit -m "feat(react): add Tooltip component"
```

Push and open a PR. The `changeset-check.yml` workflow runs and confirms the changeset is present. Merge when both `verify` (from `ci.yml`) and `changeset-check` pass.

**This validates**: User Story 1 + User Story 2 acceptance scenarios.

## Release cycle (after some PRs have merged)

After one or more PRs with changesets land on `main`, the `release.yml` workflow opens a "Version Packages" PR automatically. The PR title is `chore(release): version packages` and its diff includes:

- `version` field bumps in the affected `package.json` files
- New CHANGELOG entries combining all the descriptions from the consumed changesets
- Deletion of the `.changeset/*.md` files that contributed to the bump
- Lockfile updates if internal-dependency references changed

Review the PR diff as you would any other PR. Pay particular attention to:

- Are the version bumps the expected levels? (If a changeset said `major` but it should have been `minor`, this is your chance to catch it before publish.)
- Are the CHANGELOG entries readable and consumer-friendly?
- Are the internal `workspace:*` dependencies still aligned?

When you're satisfied, merge the "Version Packages" PR. The `release.yml` workflow detects the merge and runs `pnpm changeset publish`, which publishes the affected packages to npm at their new versions using the `NPM_TOKEN` secret.

Verify the publish succeeded by checking npm:

```sh
npm view @unbranded-ds/tokens version
npm view @unbranded-ds/react version
```

Both should report the new version numbers.

**This validates**: User Story 3 acceptance scenarios.

## Breaking change walkthrough

Same flow as above, but the changeset is `major` (or `minor` pre-1.0) and the body is the full migration guide:

````markdown
---
"@unbranded-ds/tokens": minor
---

BREAKING: rename the `themeBootstrapScript` localStorage key from `unbranded-ds-theme` to `ds-theme-v2`.

**Why**: `unbranded-ds-theme` is verbose; the v2 suffix signals intentional cleanup. (Hypothetical example only — do not actually do this without coordination.)

**Migration**:

Consumers who relied on the previous key see their saved preference fall back to the default theme on first load after upgrade. To preserve user preferences across the transition, ship a small migration script that reads from the old key and writes to the new key:

```js
const old = localStorage.getItem('unbranded-ds-theme')
if (old) {
  localStorage.setItem('ds-theme-v2', old)
  localStorage.removeItem('unbranded-ds-theme')
}
```
````

Place this script in `<head>` before the bootstrap script for a one-time migration window. After 0.5.0, the bootstrap script reads only from the new key.

````

After merge, the resulting CHANGELOG entry is the full migration guide — consumers can migrate from the CHANGELOG alone without chasing the PR or other docs (per SC-006).

**This validates**: FR-013 (content quality bar) + SC-006 (self-sufficient breaking-change CHANGELOGs).

## No-op changeset (the bypass case)

A PR that modifies a published file in a way that does not ship to consumers (a comment fix, a test-only edit) can still satisfy the CI check via an empty changeset:

```sh
pnpm changeset --empty
````

This writes a changeset with empty frontmatter and a one-line body explaining the no-op reason. It produces no CHANGELOG entry but passes `changeset-check.yml`.

**This validates**: Story 2 Acceptance Scenario 3 (empty-changeset bypass).

## What if the CI check fails on your PR?

The error message points at `.changeset/README.md` and tells you to run `pnpm changeset`. Run it, follow the prompts, commit the resulting file, push. The next CI run passes.

If you genuinely intended no consumer-facing change (you only edited a comment in source, for example), use `pnpm changeset --empty` per the no-op flow above.

## What if you accidentally pick the wrong bump level?

Two options:

- **Before merge**: edit the `.changeset/*.md` file directly. Change the frontmatter bump level, commit, push.
- **After merge but before the Version Packages PR is reviewed**: add a follow-up changeset that adjusts the bump. Changesets resolves multiple changesets affecting the same package by taking the highest severity (e.g., `major` + `patch` = `major`).

## What if a release fails partway?

Changesets' `publish` step is idempotent. If `@unbranded-ds/tokens` published but `@unbranded-ds/react` failed (npm flake, network issue), re-running the workflow picks up where it left off — it checks the registry first and only publishes packages whose `version` on disk is not yet on the registry.

Re-trigger the release workflow by pushing an empty commit to `main`, or by manually re-running the failed workflow run from the GitHub Actions UI.

## Migrating from 0.1.0 / 0.2.0 era CHANGELOGs

The 0.2.0 entries in `packages/tokens/CHANGELOG.md` and `packages/react/CHANGELOG.md` were hand-authored before this workflow landed. They are preserved as-is per FR-009. A header note above each 0.2.0 entry points future readers at `.changeset/README.md` for context.

From 0.3.0 onward, every entry is auto-generated. The 0.2.0 entries are the one-time exception.
