# Phase 1 Data Model: Versioning and release workflow

No persistent database model. The "data" here is a set of filesystem artifacts that the workflow reads, writes, and consumes. This document captures their shapes, validation rules, and lifecycle transitions.

## Entities

### E1 — `.changeset/config.json` (workspace-level configuration)

**Path**: `.changeset/config.json` at the repo root.

**Lifecycle**: Created once during `pnpm changeset init` (or hand-written from the contract). Edited rarely; changes to it affect every future release.

**Shape** (TypeScript-style):

```ts
type ChangesetConfig = {
  $schema?: string
  changelog: string | [string, unknown]  // formatter ID; default "@changesets/cli/changelog"
  commit: boolean | [string, unknown]    // false; Version Packages PR handles commits
  fixed: string[][]                       // []; packages bump independently
  linked: string[][]                      // []; same reason
  access: "public" | "restricted"        // "public"
  baseBranch: string                      // "main"
  updateInternalDependencies: "patch" | "minor"  // "patch"
  ignore: string[]                        // package names excluded from version bumps
}
```

**Required field values for this monorepo** (per FR-002 and clarifications):
- `access: "public"` — matches existing `publishConfig` on both packages
- `baseBranch: "main"`
- `updateInternalDependencies: "patch"` — supports FR-012
- `ignore: ["@unbranded-ds/storybook"]` — supports FR-011 (storybook app is not published)

**Validation**: The Changesets CLI rejects invalid configs at parse time. No additional validation needed from this spec.

### E2 — `.changeset/*.md` (per-PR changeset file)

**Path**: `.changeset/<unique-name>.md` (typically a memorable two-word slug auto-generated by `pnpm changeset`).

**Lifecycle**: Created when a contributor runs `pnpm changeset` during a PR. Lives on the feature branch and merges to `main`. Consumed by `pnpm changeset version` (at release time), which converts its content into CHANGELOG entries and deletes the file.

**Shape**: a markdown file with YAML frontmatter declaring package bumps, then a free-form body containing the change description.

```markdown
---
"@unbranded-ds/tokens": minor
"@unbranded-ds/react": patch
---

Short summary of the change. For non-breaking changes this can be one line.

For breaking changes, a multi-paragraph migration guide goes here:

- Before: `import { foo } from '@unbranded-ds/tokens/dist/...'`
- After:  `import { foo } from '@unbranded-ds/tokens/foo'`

Why: the dist path was leaking internal package layout.
```

**Validation**:
- Frontmatter package names MUST appear in `pnpm-workspace.yaml`. The CLI rejects unknown packages.
- Bump levels MUST be `major`, `minor`, or `patch`. Any other string is rejected.
- The body MAY be empty for no-op changesets (per Story 2 Acceptance Scenario 3), in which case it produces no CHANGELOG entry but satisfies the CI presence check.
- Per FR-013, breaking-change bodies (any changeset with `major` bump pre-1.0, or `minor` for a pre-1.0 breaking change) MUST contain the migration content described in FR-013. This is a content-quality requirement enforced by review, not by tooling.

### E3 — Per-package `CHANGELOG.md`

**Path**: `packages/tokens/CHANGELOG.md` and `packages/react/CHANGELOG.md`.

**Lifecycle**: Initialized by spec 002 with hand-authored 0.2.0 entries. From spec 003 onward, the file is appended to by `pnpm changeset version` whenever a release ships.

**Shape**: standard Changesets-default CHANGELOG format:

```markdown
# @unbranded-ds/<pkg>

> [Header note about the 0.2.0 one-time exception — see R7]

## 0.3.0

### Minor Changes

- abc1234: <body content from a minor changeset>

### Patch Changes

- def5678: <body content from a patch changeset>

## 0.2.0

[Hand-authored 0.2.0 content from spec 002 — preserved verbatim per FR-009]
```

**Validation**:
- The file is tool-owned from 0.3.0 onward. Contributors do not hand-edit it.
- The 0.2.0 section and the header note are the only hand-authored content.

### E4 — "Version Packages" pull request

**Path**: a transient PR on the GitHub repo, opened by `changesets/action`.

**Lifecycle**: Opened when one or more `.changeset/*.md` files exist on `main`. Updated automatically every time additional changesets land on `main`. Closed (auto-merged or manually merged) by the release shepherd, which triggers the publish step.

**Shape**: a PR whose diff against `main` includes:
- `version` field bumps in `packages/tokens/package.json` and/or `packages/react/package.json`
- New entries appended to `packages/tokens/CHANGELOG.md` and/or `packages/react/CHANGELOG.md`
- Deletion of every `.changeset/*.md` file that contributed to the bump
- Updates to `pnpm-lock.yaml` if internal-dependency references changed (per `updateInternalDependencies: "patch"`)

**Validation**: The diff is auto-generated by Changesets; manual review by the release shepherd is the only validation.

### E5 — `.changeset/README.md` (contributor doc)

**Path**: `.changeset/README.md`.

**Lifecycle**: Created once as part of this spec's implementation. Edited rarely (when the workflow itself changes).

**Shape** (per FR-010): a markdown file covering:
- When to run `pnpm changeset` (every PR that modifies `packages/`)
- How to pick a bump level (`major` for breaking, `minor` for additions, `patch` for fixes)
- What to write in the description (with the FR-013 quality bar explicit)
- What happens after the PR merges (Version Packages PR → publish)
- A worked example of a breaking-change changeset (multi-paragraph migration content)
- A worked example of a non-breaking changeset (one-liner)

**Validation**: Manual review; the doc is prose.

## Relationships

```text
.changeset/config.json
    ↓ (read by)
pnpm changeset
    ↓ (creates)
.changeset/<slug>.md     (one per PR)
    ↓ (merged to main, then read by)
pnpm changeset version
    ↓ (modifies)
packages/<pkg>/package.json   (version field)
packages/<pkg>/CHANGELOG.md   (new entry appended)
pnpm-lock.yaml               (internal-dep ref updated)
.changeset/<slug>.md         (deleted)
    ↓ (visible in)
"Version Packages" PR
    ↓ (when merged, triggers)
pnpm changeset publish
    ↓ (publishes to)
npm registry
```

## State transitions

A single changeset file moves through three states:

1. **Pending** — exists on a feature branch or on `main` but not yet consumed. Counted by `pnpm changeset status`.
2. **Staged for version bump** — included in the open "Version Packages" PR. Still on disk; still pending until the PR is merged.
3. **Consumed** — deleted from disk when the "Version Packages" PR merges. Its content has been integrated into the affected CHANGELOG.md files.

Once consumed, the file is gone. The CHANGELOG entries that came from it are the durable record.
