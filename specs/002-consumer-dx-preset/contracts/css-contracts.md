# Contract: CSS file structure

The CSS files exposed via `./preset.css` on both packages have strict structural contracts. These are what Tailwind v4 sees when a consumer imports them, and any deviation can break consumer overrides or theme registration.

## `@unbranded-ds/tokens/preset.css`

**Resolves to**: `packages/tokens/dist/tailwind/preset.css` (unchanged content, new clean alias)

**Contract**:

1. The file MUST contain exactly one top-level construct: a single `@theme inline { ... }` block.
2. Every declaration inside the block MUST be a Tailwind v4 token-name-to-CSS-variable mapping of the form:
   ```css
   --<category>-<key>: var(--<category>-<key>);
   ```
3. The file MUST NOT contain any declaration that sets a value (no `--color-background: #fff`). Default values live in `packages/tokens/dist/css/tokens-{light,dark,brand}.css` and are reached via the `./themes/<name>.css` export.
4. The file MUST NOT contain any `@import` directives. It is leaf content for the consumer's Tailwind build.
5. The file is generated by Style Dictionary via the `tailwind/theme-inline` custom format declared in `packages/tokens/sd.config.ts`. Manual edits MUST NOT be added; changes flow through the SD config.

**Why registration-only matters**: The `@theme inline` block tells Tailwind "the utility name `bg-primary` resolves to whatever the CSS variable `--color-primary` is set to." It does not set `--color-primary` to a value. Consumers can then declare `:root { --color-primary: oklch(...) }` lower in their cascade and have their value win. If this preset inlined defaults, consumers' overrides would have to fight a same-specificity ancestor declaration, breaking the "schema locked, values float" design (constitution Section III).

**Verification**: a test or lint rule scans the file and asserts:
- Every declaration matches the `--<x>: var(--<x>)` pattern
- No declarations contain anything else (no hex, oklch, rem, px values)

## `@unbranded-ds/react/preset.css`

**Resolves to**: `packages/react/dist/preset.css` (new file)

**Source**: `packages/react/src/preset.css` (hand-authored, two-line file)

**Contract**:

1. The file MUST contain exactly two directives:
   ```css
   @import '@unbranded-ds/tokens/preset.css';
   @source "../@unbranded-ds/react";
   ```
2. The `@source` path MUST be relative to the file's location in `node_modules/@unbranded-ds/react/dist/`, resolving to `node_modules/@unbranded-ds/react` so Tailwind scans all of the React package's compiled output for utility class names.
3. The file MUST NOT add any other directives, declarations, or comments that would constrain the consumer's Tailwind configuration.
4. The file is hand-authored at `packages/react/src/preset.css` and copied to `dist/preset.css` via the `onSuccess` hook in `tsup.config.ts`. Source and dist content match byte-for-byte.

**Why `@source` belongs here (not in tokens)**: `@source` is a Tailwind v4 directive that tells the compiler "scan these files for utility class names you might miss." It is necessarily framework-specific — the path points at the React package's compiled JSX. Putting this in `@unbranded-ds/tokens/preset.css` would force every consumer (including Vue, Svelte, vanilla HTML) to pay for a scan of a React package they may not be using, breaking the "tokens are independent of components" principle (constitution Section II).

**Verification**: a build-time test asserts the dist file content is exactly the source content, and that the source content matches the two-directive contract above (no drift, no copy errors).

## The cascade contract (consumer-side)

This is not a file we ship, but a documented expectation of how consumers compose their stylesheet:

```css
/* consumer's globals.css */
@import 'tailwindcss';
@import '@unbranded-ds/react/preset.css';

/* OPTIONAL: bring in upstream's default values */
@import '@unbranded-ds/tokens/themes/light.css';
@import '@unbranded-ds/tokens/themes/dark.css';

/* OPTIONAL: consumer's own overrides */
:root {
  --color-primary: oklch(0.5 0.2 240);
}
```

**Contract**:

1. Tailwind is imported first by the consumer (we never import Tailwind from inside our preset).
2. Our preset.css is imported next — registers Tailwind utility names backed by CSS variables.
3. Optional theme defaults next — provide values for the registered variable names.
4. Optional consumer overrides last — win by cascade order, not by selector specificity.

Removing or reordering any of these lines is the consumer's call. The contract is that our two preset files do not assume any particular ordering of the optional lines.
